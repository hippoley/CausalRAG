# Branchpoint launch kit

This is not a press release. It is a reusable distribution surface for one falsifiable claim:

> A model can propose an action. It should not automatically inherit the authority to execute it.

The launch should always point to something people can run, inspect, or challenge.

## The receipt

Same world. Same proposer. Same goal.

- naive loop: `submit_form -> session_expired -> failure`
- Branchpoint: `inspect_submission_state -> reauthenticate -> success`

**Title**

> Show HN: Branchpoint – same model, same world, different execution boundary

**Opening comment**

I built Branchpoint because I kept seeing one boundary collapsed in agent loops:

`model proposes -> tool executes`

The model may be good at ranking a next action, but that does not mean it should inherit execution authority.

The smallest example is a browser action. The proposer wants to `submit_form`.

In the frozen test world, a proposal-order loop executes it immediately and fails because the session has expired.

Branchpoint takes the same proposal in the same world, inserts a read-only observation first, discovers `session_expired`, then chooses `reauthenticate` and succeeds.

The Pages demo is generated from the Python runtime in CI rather than from a frontend simulation:

## Reply bank

When someone says **"this is just guardrails"**:

> Partly. The difference I am testing is broader than block/allow: the runtime can choose a read-only observation, wait, ask a human, update state, or change the next intervention. I am trying to find the smallest abstraction that deserves to exist outside the proposer.

When someone says **"just put this in the system prompt"**:

> That is exactly the boundary I want to test. A prompt can influence the proposal. It cannot by itself provide an independently enforceable execution policy, trusted state, or a reproducible same-world comparison.

When someone says **"the example is contrived"**:

> Yes — intentionally. It is a deterministic fixture for isolating one variable. The next useful step is collecting real failure cases where the same boundary matters, and cases where it does not.

When someone asks **"how is this different from LangGraph / an orchestrator?"**:

> I am not trying to replace orchestration. Branchpoint is narrower: it focuses on the decision boundary between candidate actions and execution, with explicit uncertainty, runtime-owned policy, evidence updates, and replay.

When someone finds a real flaw:

> Good. Please reduce it to the smallest reproducible world you can. A failing fixture is more valuable to this project than a supportive comment.
