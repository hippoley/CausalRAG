# v0.3 — Competing hypotheses and falsification

Branchpoint v0.3 adds an explicit epistemic layer between causal beliefs and actions.

The important change is not that the model can *mention* several explanations. The runtime now persists them as state and records which action was selected to distinguish or falsify them.

```text
Goal
  ↓
Causal beliefs + competing hypotheses
  ↓
Which uncertainty matters for the decision?
  ↓
Which observation can separate H1 / H2 / H3?
  ↓
Observe / retrieve / ask / intervene
  ↓
Support, conflict, or falsifier evidence
  ↓
Update hypothesis state
  ↓
Replan
```

## Why this is more agentic

A normal answer-oriented system can say:

> The low airflow may be caused by a clogged filter or a weak fan.

That is still only narration.

A falsification-oriented agent instead keeps both explanations alive and asks:

> What is the cheapest, safest observation whose possible outcomes would change which explanation I believe?

For example:

```text
H1  clogged filter       credence 0.60
H2  underperforming fan  credence 0.40

candidate observation:
read_filter_pressure

why:
normal pressure drop would count against H1
```

If the observed pressure drop is normal, the runtime stores that result as conflicting/falsifying evidence for H1 instead of merely appending it to a chat transcript.

The repository includes a deterministic demo that does not need an LLM or API key:

```bash

```

The trace exposes both the epistemic state and the purpose of the selected action:

```python
payload = result.to_dict()

for hypothesis in payload["hypotheses"]:
    print(
        hypothesis["id"],
        hypothesis["probability"],
        hypothesis["status"],
        hypothesis["falsifiers"],
    )

first_action = payload["decisions"][0]["selected"]
print(first_action["tests_hypotheses"])
print(first_action["falsification_target"])
```

## Runtime objects

### `Hypothesis`

A hypothesis is persistent world-model state with:

```text
id
statement
probability
rationale
falsifiers
supporting_evidence
conflicting_evidence
status
version
```

`status` is currently a small operational convenience:

- `active`: unresolved
- `supported`: credence >= 0.90
- `rejected`: credence <= 0.10

### `CandidateAction.tests_hypotheses`

An information-seeking action can declare which hypotheses its outcome is expected to discriminate between.

### `CandidateAction.falsification_target`

An action can name one hypothesis for which at least one possible result would be meaningful counterevidence.

This metadata is written into the transition trace, so later evaluation can ask whether the agent actually selected informative experiments instead of merely producing plausible explanations.

## Compatibility is not support

The reasoner prompt and hypothesis updater intentionally distinguish these:

```text
observation is compatible with H1
!=
observation discriminates in favor of H1
```

An observation should not increase a hypothesis merely because the hypothesis can accommodate it. Positive updates should be reserved for evidence that is actually diagnostic relative to relevant alternatives.

This is the first defense against confirmation-seeking retrieval.

## Probability semantics in this slice

The current `Hypothesis.probability` value is a **bounded operational credence**, updated by signed evidence weights.

It is **not yet** a normalized Bayesian posterior and competing hypotheses are **not required to sum to 1**.

That is deliberate for this slice. v0.3 first establishes the stable runtime contract:

```text
competing hypotheses
→ explicit falsifiers
→ diagnostic action
→ observation
→ signed evidence
→ persistent update
```

Once that behavior is observable and testable, a later estimator can replace the update rule without redesigning the agent loop.

## What the LLM controls — and what it does not

The LLM may propose:

- candidate hypotheses;
- falsification conditions;
- candidate actions;
- which hypotheses an action tests;
- signed evidence updates after an observation.

The LLM does **not** own:

- persistent world state;
- capability cost/risk/reversibility metadata;
- final action selection;
- execution rights;
- the mechanics of state persistence.

The runtime remains the authority around the model.

## Next mathematical layer

The next useful step is not more prompting. It is to reduce dependence on model-estimated `expected_information_gain`.

A later slice should give the runtime a deterministic discrimination / value-of-information score based on the current hypothesis set and expected observation outcomes. That can then support metrics such as:

```text
information gain per cost
hypothesis calibration
falsification efficiency
unnecessary action rate
causal regret
```

After that, experiment contracts and a HiddenWorld benchmark can test whether the agent actually learns a causal environment under an action budget.
